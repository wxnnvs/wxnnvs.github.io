SEB Integrity Checks: Config Key and Browser Exam Key

A practical guide for exam platform developers who want to verify that students are using a legitimate, unmodified Safe Exam Browser (SEB) installation.

1. What Are These Keys?

Config Key (CK): Verifies that the SEB configuration (the .seb file settings) is correct and unmodified. It does not verify the SEB application binary itself. It is platform-independent (Windows, macOS, iOS generate the same CK for the same settings) and does not change when SEB is updated, as long as the settings remain the same[reference:0].

Browser Exam Key (BEK): Verifies both the SEB configuration and the SEB application binary (code signature). It changes if the SEB version changes, if the OS platform changes, or if someone compiles a modified SEB with disabled restrictions. This is the stronger check because it can detect a tampered SEB build[reference:1].

Recommendation: Use Browser Exam Key whenever possible. It is the only key that detects a student running a modified SEB binary. Config Key alone only ensures the settings file is correct, not that the browser executable is legitimate.

2. How SEB Sends These Keys

When SEB makes an HTTP request to your exam platform, it includes one or both of these headers, depending on your configuration:

Key Type HTTP Header Name
Browser Exam Key X-SafeExamBrowser-RequestHash
Config Key X-SafeExamBrowser-ConfigKeyHash

Both headers contain a SHA-256 hash of the URL of the request concatenated with the key. This means the hash changes for every URL, keeping the key secret from network sniffers[reference:2][reference:3].

Header value format (example):

X-SafeExamBrowser-RequestHash = 81aad4ab9dfd447cc479e6a4a7c9a544e2cafc7f3adeb68b2a21efad68eca4dc

3. How Verification Works on the Server

For each incoming request, your exam platform must:

  1. Extract the header value, for example X-SafeExamBrowser-RequestHash.
  2. Reconstruct the expected hash:
    • Concatenate the full request URL with the stored key (BEK or CK).
    • Important: The URL must match exactly what SEB used. This includes the protocol (https://), host, path, and query string. A mismatch (for example, example.com vs www.example.com) will cause verification to fail[reference:4].
  3. Hash the concatenated string using SHA-256.
  4. Compare the computed hash with the header value.

Concatenation Order

  • For Config Key: URL + ConfigKey (URL first, then key)[reference:5].
  • For Browser Exam Key: URL + BrowserExamKey (same order)[reference:6].

Pseudocode

function verifySEBRequest(requestURL, storedKey, receivedHeaderValue):
    combined = requestURL + storedKey
    computedHash = SHA256(combined).hex()
    return computedHash == receivedHeaderValue

Important: Remove any #fragment from the URL before hashing.

4. How to Generate the Keys Server-Side

If your exam platform generates .seb configuration files automatically, you should also generate the corresponding Config Key and Browser Exam Key server-side. This avoids manual copy-paste errors[reference:7].

Config Key Generation

The Config Key is computed from the SEB settings dictionary. The algorithm is:

  1. Parse the .seb configuration (an XML plist or JSON structure)[reference:8].
  2. Set sebConfigPurpose to the value used for starting an exam[reference:9].
  3. Serialize the settings dictionary in SEB's deterministic order (using .NET's StringComparer.InvariantCulture ordering)[reference:10].
  4. Skip the originatorVersion field[reference:11].
  5. Compute a SHA-256 hash of the resulting byte string[reference:12].

This produces a 64-character hex string.

Critical detail: SEB does not use standard JSON for hashing. It uses a "JSON-ish" format called SEB-JSON where string contents are written without character escaping. For example, a string containing a quotation mark is written as-is, not escaped. Using a standard JSON encoder will produce a different hash[reference:13].

Browser Exam Key Generation

The Browser Exam Key adds a code signature of the SEB application to the mix:

  1. Start with the same settings dictionary used for Config Key.
  2. Add a code signature of the SEB application (binaries and resources). How this signature is generated is platform-specific[reference:14].
  3. Add a salt value, generated randomly each time a .seb file is saved[reference:15].
  4. Compute SHA-256 of the combined result.

Because the code signature differs per platform and per SEB version, you need a separate BEK for each platform (Windows, macOS, iOS) that your exam supports[reference:16].

5. Implementation Checklist for Your Exam Platform

Step Action
1 Enable SEB to send keys: In your .seb config, set sendBrowserExamKey = true[reference:17].
2 Store the expected BEK and/or CK in your exam settings (per quiz/exam).
3 On every exam page request, check for the X-SafeExamBrowser-RequestHash and/or X-SafeExamBrowser-ConfigKeyHash headers.
4 Reconstruct the hash using the exact request URL and the stored key.
5 Compare the computed hash with the header value. If they don't match, deny access.
6 If using Config Key, generate it server-side from your .seb file to avoid manual errors[reference:18].
7 Password-lock your .seb config files so students cannot extract and reuse the keys.

6. Common Pitfalls

  • URL mismatch: The URL on the client and server must be byte-identical. Check for www. prefixes, trailing slashes, and protocol differences (http vs https).
  • Using standard JSON for Config Key: SEB-JSON does not escape strings. Using json_encode() in PHP or JSON.stringify() in JavaScript will produce the wrong hash[reference:19].
  • Checking only Config Key: A student with a modified SEB binary will still pass the Config Key check because the settings are unchanged. Always prefer Browser Exam Key for high-stakes exams[reference:20].
  • Missing keys in SPAs: If your exam is a single-page application, SEB will not update the hash for client-side route changes. Ensure the URL used for verification reflects the correct state[reference:21].

7. Reference Implementations

  • Moodle: The quizaccess_seb plugin implements both CK and BEK verification. It defines the header constants and performs the SHA-256 hash comparison in the access_manager class.
  • Node.js: The @certible/seb-node package provides generateConfigKey() and verifyConfigKeyHash() functions for server-side use[reference:22].
  • PHP: The cameron1729/seb-json package encodes PHP data structures into the correct SEB-JSON byte format for Config Key generation[reference:23].

8. Summary

The Config Key verifies the settings. The Browser Exam Key verifies the settings plus the SEB binary. Both are sent as SHA-256 hashes of the request URL concatenated with the key. Your exam platform must reconstruct this hash using the exact URL and compare it to the header value. For strong security, use Browser Exam Key and generate the keys server-side to eliminate manual errors.
